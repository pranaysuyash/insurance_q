# App Store and Google Play Readiness: Backend Security and Privacy

**Date:** 2026-10-12  
**Lane:** Backend production readiness, security, privacy, feature completeness  
**Verdict:** **NO-GO for public store launch on backend evidence currently available.**  
**Evidence tier:** Tier 1, static inspection only. No tests, package installs, Git commands, production-service calls, or runtime changes were performed. Public Apple and Google policy documentation was consulted for store-category terminology and account-deletion requirements.

## Scope and evidence boundary

Inspected the current `render.yaml`, FastAPI entrypoint and routers, worker, settings and runtime configuration, upload validation, service repositories, migrations, and the requested product and readiness documents. The findings below describe source behavior. They do not establish current Render environment values, deployed image, public reachability, Supabase production policy state, provider retention settings, or current App Store Connect / Play Console submissions. No production service or store console was accessed.

The user prohibited Git commands. Therefore, whether any credential-like content is tracked or committed, and whether it remains valid, is **UNVERIFIED**. The only secret scan conclusion in this report is that one password-like value is present in the current working tree at the cited location. The value is intentionally redacted.

## Current backend controls observed

- `render.yaml` defines a Render web service and worker, pins production backends to Supabase, and declares dashboard-only secrets with `sync: false`. The API uses `/health` as its Render health path. These declarations do not prove that the services exist or that required dashboard values are populated (`render.yaml:20-76`, `render.yaml:78-120`).
- The API lifespan invokes `production_configuration_errors` and fails startup when required production values are absent. Production CORS requires explicit origins and hosts, rejects wildcard values, and disables credentialed CORS. Debug and retired routes use a production guard (`src/app/main.py:63-80`, `src/app/main.py:115-128`, `src/utils/runtime_config.py:47-71`, `src/utils/runtime_access.py:14-17`).
- Authenticated policy, document, claim, family, evidence, consent, analytics, subscription, and QA-report routes use `get_current_user`; the RevenueCat webhook uses its own shared-secret check. Public exceptions include anonymous identity issuance and capabilities bootstrap. The public web deletion endpoint is a security exception with a separate finding below (`src/api/user.py:79-117`, `src/api/user.py:203-218`, `src/api/user.py:470-541`, `src/api/capabilities.py:35-54`, `src/api/subscription.py:283-338`).
- RLS is enabled on core documents and chunks, claims, family members, and several service-only tables. Many backend clients use the service role, which bypasses RLS. The inspected document repository filters by both document ID and owner, vector search requires an owner filter, and claims and family queries scope records to the verified principal. Static inspection did not establish remote policy parity or provide runtime cross-principal proof (`supabase/migrations/20260717000000_coverwise_schema.sql:7-18`, `supabase/migrations/20260717000000_coverwise_schema.sql:114-122`, `src/services/document_repository.py:343-394`, `src/services/supabase_vector_store.py:86-108`, `src/api/claims.py:110-163`, `src/api/family.py:52-62`).
- Upload validation enforces a 50 MiB per-file limit, extension allowlisting, content signatures, PDF page bounds, and image pixel bounds. Production upload rate limits use a Supabase RPC, and policy uploads reserve server-side entitlement slots. Canonical JSON and streaming Q&A routes reserve from the server-side usage ledger. The legacy form query route does not (`src/utils/upload_validation.py:19-23`, `src/utils/upload_validation.py:43-61`, `src/api/document.py:206-288`, `src/app/main.py:493-521`, `src/app/main.py:684-709`).

### Data-flow and retention notes

- `src/rag/pipeline.py:452-470` sends policy-derived text to the OpenAI embeddings API. Retrieved policy context and the authenticated user's question are assembled into the model prompt at `src/rag/pipeline.py:1378-1434`; the model client issues chat-completion calls at `src/llm/client.py:280-297`. `src/app/main.py:544-552` forwards the authenticated user's question and owner-scoped filters into document processing.
- Supabase is configured as the production database, vector store, and object store. The core migration creates the `coverwise-documents` bucket with `public = false` (`render.yaml:34-40`, `supabase/migrations/20260717000000_coverwise_schema.sql:143-145`). No live bucket configuration was checked.
- Sentry is optional in the Render blueprint. If enabled, source currently opts into default PII collection. Sentry and Render retention settings were not accessible under this audit scope.
- Account deletion has a durable worker path, but queued jobs and deletion request audit rows can themselves carry account identifiers. Retention for those records and backups is not established by this static inspection.

## Route authentication and ownership assessment

Static route inspection found owner authentication on the user-data endpoints for documents, claims, family, evidence, consent, analytics ingestion, subscriptions, and QA reporting. The webhook uses a dedicated authorization check. Anonymous identity issuance and capability bootstrap are intentionally public. Diagnostic routes are intended to be non-production only. The concrete public deletion issue is SEC-01. `/metrics` and health diagnostics are covered by SEC-11.

For the sampled data paths, Supabase RLS is enabled on core data tables, with explicit owner policies for claims/family and server-only grants on service-owned data. Because backend service-role clients bypass RLS, current API/service owner filters are an essential control. Source checks confirm filters on document reads/writes, vector searches, claims, family records, and evidence document ownership. No live cross-principal negative request was performed, and no current production migration or policy state was queried.

## Recommended remediation order

1. Close SEC-01 and SEC-02 before exposing the public API or submitting binaries. SEC-02 requires credential-owner confirmation and rotation even though the credential's validity and tracking state could not be established under this audit's restrictions.
2. Replace the deletion/export contract using a canonical per-user data inventory. Include every account-linked table, object, vector, derived artifact, queued job, and provider-bound record, then prove completion with owner-scoped postconditions.
3. Remove or unify the deprecated query endpoint so all Q&A traffic uses the same server-side budget ledger.
4. Add worker boot configuration validation, close upload aggregate limits, restrict metrics, sanitize health output, minimize PII in logs and Sentry, and validate analytics event properties.
5. Reconcile stale deployment comments and debt statuses, verify Render worker health behavior and populated production configuration, then complete the exact-head and live deletion/isolation checks required by P0-4 and P0-7.
6. Reconcile the backend renewal/contact boundary with the canonical wedge and finalize store data-safety answers from actual deployed payload and provider settings.
