# DI / Service Architecture Deep Dive — 2026-07-22

## Why This Matters

Every architectural decision flows from how services are wired together. If the DI pattern is tangled, every new feature, every test, every refactor becomes harder than it needs to be. We've already felt this — the `ConsentSyncService` optional `Dio` override, the `EvidenceService` authenticatedDio bug, the `PolicyExtractionService` missing auth interceptor, the tests that can't touch `AuthService` at all. These aren't isolated incidents. They're symptoms.

## The Three Patterns

The codebase has three coexisting DI approaches across 23 service classes:

| Pattern | Count | Services | Testable? |
|---------|-------|----------|-----------|
| **All-static** | 9 | AuthService, AnalyticsService, SessionService, InstallService, AppStateRepository, NotificationService, ContactService, LeadGenerationService, PreventiveHealthService | No (static mutable state leaks, can't mock) |
| **Instance via Riverpod** | 5 | DocumentService, QueryService, PolicyExtractionService, RelationshipExtractionService, EvidenceService | Yes (constructor injection) |
| **Singleton** | 3 | PrincipalKeyService, ConsentSyncService, HiveWorkspaceService | Partial (factory with fallback) |
| **Instance (direct)** | 3 | LocalStorageService, ServerConsentService, EntitlementService | Partial (hardcoded defaults) |
| **Static-only** | 3 | MlOcrService, DemoService, DragDropService | Yes (pure functions or safe static) |

### The Static Pattern (most common, most problematic)

```dart
// session_service.dart
class SessionService {
  static String? _currentSessionId;
  static String getSessionIdSync() { ... }
}

// auth_service.dart
class AuthService {
  static const FlutterSecureStorage _secureStorage = FlutterSecureStorage();
  static bool _accountClientReady = false;
  static Future<void> initializeAccountClient() async { ... }
}
```

Every call is `SessionService.getSessionIdSync()` or `AuthService.signIn()`. The class is essentially a namespace. Dependencies are accessed via other static Hive box references or static service calls.

**What this means**:

- **You cannot write a unit test for any consumer of AuthService.** Nothing mocks it. Nothing intercepts it. The 73 test files in this project call `AuthService.*` exactly zero times. Not because auth doesn't need testing — because it can't be tested.

- **AnalyticsService is cleaned up in HiveTestHelper.tearDown.** The test infrastructure has to explicitly dispose a global service because the service itself is global. If another test forgets to call `AnalyticsService.dispose()`, the timer keeps running and the isolate hangs.

- **Startup order is implicit and enforced by crash.** There's no graph. You just call the things in the right order in `main.dart` and if you get it wrong, you get a runtime error. A future developer who adds a new static service that depends on another static service won't know until they hit the crash.

### The Instance Pattern (clean, but incomplete)

```dart
// service_providers.dart
final _dioProvider = Provider<Dio>((ref) { ... });
final documentServiceProvider = Provider<DocumentService>((ref) {
  return DocumentService(ref.watch(_dioProvider));
});
```

This is the right pattern. `DocumentService` takes a `Dio` in its constructor. The provider creates it. Tests create their own `DocumentService(mockedDio)`. No global state, no cleanup problems.

**But only 2 services are wired this way.** The other 21 services find other routes.

### The authenticatedDio Leak (static + instance = worse)

```dart
// document_service.dart
class DocumentService {
  static Dio? _authenticatedDio;
  static Dio get authenticatedDio {
    if (_authenticatedDio == null) { ... }
    return _authenticatedDio!;
  }
}
```

This is a static singleton of a network client. 5 different consumers reference it:

1. `EvidenceService` — constructor default
2. `AnalyticsService` — direct static call in sync
3. `ServerConsentService` — constructor default
4. `BillingAdapter` — direct static calls
5. `ProcessingStatusScreen` — direct in `initState`
6. `DocumentService` itself — uses it internally for delete/status calls

The `ProcessingStatusScreen` explicitly documents the problem:

```dart
// DocumentService.authenticatedDio is a process-wide shared client. This
// screen must not close it while other screens or providers may still be
// using the same interceptor/client instance.
```

Translation: "nobody owns this, so nobody can clean it up."

## Concrete Issues Found

### 1. PolicyExtractionService: Missing AuthInterceptor

`policy_extraction_service.dart:13-17` creates its own Dio without AuthInterceptor:

```dart
final Dio _dio = Dio(BaseOptions(
  baseUrl: AppConfig.baseUrl,
  connectTimeout: ...,
  receiveTimeout: ...,
));
```

This was **already identified and fixed** in `EvidenceService` (see the doc comment at `evidence_service.dart:20-26`). The exact same bug exists in `PolicyExtractionService`. Calls to `/documents/$id/summary` go out without a Bearer token. The server likely returns 401 or 403, which means the fallback (13 sequential LLM queries on the device) runs every time. This is probably a real performance issue in production.

### 2. AuthService: Zero Test Coverage

73 test files. Zero references to `AuthService.signIn`, `AuthService.initializeAccountClient`, `AuthService.accessToken`, `AuthService.signOut`, or `AuthService.deleteAccount`. The auth flow — the most security-critical code in the app — has no automated tests at all. The class uses static `FlutterSecureStorage` and static `Hive.box` references, so a test would need real hardware-backed secure storage or elaborate mocking of platform channels.

### 3. Static State Leaks Between Tests

- `AnalyticsService._buffer` — static list, not cleared between tests
- `AnalyticsService._syncTimer` — static timer, must be disposed manually
- `SessionService._currentSessionId` — static cache, persists across tests
- `InstallService._cachedInstallId` — static cache, persists across tests

The test suite works today because `HiveTestHelper.tearDown` calls `AnalyticsService.dispose()`, but if any test reads `SessionService.getSessionIdSync()` before calling `HiveTestHelper.setUp()`, it gets stale data or crashes. The only reason this hasn't caused flaky tests is that every test file happens to call `setUp` first. This is an accident waiting to happen.

### 4. ConsentSyncService: Factory Hack for Testability

`consent_sync_service.dart:17-20`:

```dart
factory ConsentSyncService({Dio? dio}) {
  if (dio != null) return ConsentSyncService._(dio: dio);
  return _instance;
}
```

The factory creates a new instance whenever a Dio is passed for testing. This works, but it undermines the singleton pattern's purpose — every production call to `ConsentSyncService()` gets the singleton, but test calls create ephemeral instances. The dedup logic (`_inFlight`) lives on the instance, so test instances don't dedup against the production singleton. This is a design smell: the pattern was bent to enable testing rather than designed for it.

### 5. ServerConsentService: Hardcoded authenticatedDio Default

`server_consent_service.dart:21-22`:

```dart
ServerConsentService({Dio? dio})
    : _dio = dio ?? DocumentService.authenticatedDio;
```

This was added as part of our sync integration test work. It improves on the previous version which was a hard `DocumentService.authenticatedDio` with no override at all. But the default still ties it to a static singleton. A clean constructor would require `Dio` and let the provider layer wire it.

### 6. Mixed Patterns in Screens

`processing_status_screen.dart:123`:

```dart
late final Dio _dio = DocumentService.authenticatedDio;
```

A screen directly accessing a static Dio. This skips the entire provider layer. If the auth token expires, this screen has no way to react — it doesn't go through `AuthInterceptor` in a managed way, and it can't be tested without the real `DocumentService.authenticatedDio` being initialized.

## The Core Design Tradeoff

The static pattern was probably chosen for **simplicity** — no provider wiring, no constructor injection, just call `AuthService.signIn()` from anywhere. This works well for small apps. CoverWise is past that size.

The threshold is crossed when:
- You have more than ~10 service files
- You want to unit test service consumers
- Services depend on other services (AuthService -> SessionService -> Hive)
- Startup order matters and can't be inferred
- You need to swap implementations (e.g., mock server in tests)

CoverWise crosses all five thresholds.

## Recommendations

### Tier 1 (High Impact, Low Effort)

1. **Fix PolicyExtractionService Dio** — Add AuthInterceptor to its Dio instance. Two lines. Confirmed by the EvidenceService fix as the right pattern. This is probably actively causing the backend summary fallback to run on every request.

2. **Wire the remaining 3 instance services through Riverpod** — `EntitlementService`, `ServerConsentService`, `LocalStorageService` already accept dependencies in constructors. They just need a provider entry.

### Tier 2 (Medium Impact, Medium Effort)

3. **Eliminate `DocumentService.authenticatedDio`** — Replace with a `authenticatedDioProvider` in `service_providers.dart`. Every consumer switches from `DocumentService.authenticatedDio` to `ref.watch(authenticatedDioProvider)`. The Dio lifecycle is then managed by Riverpod's `ref.onDispose`.

4. **Riverpod-ify static query-adjacent services** — `NotificationService`, `ContactService`, `LeadGenerationService`, `PreventiveHealthService` are mostly pure functions or thin Hive wrappers. They don't need to be services at all — they could be Riverpod providers or utility classes. This shrinks the static surface area by 4 files with minimal risk.

### Tier 3 (Structural, Coordinate with Resets)

5. **AuthService as a Riverpod provider** — The biggest lift. AuthService has the most state (secure storage, Supabase client, token cache) and is the most tested (zero). The migration path:
   - Create `authServiceProvider` that initializes Supabase and manages auth state as a `Notifier`
   - Screens watch the provider instead of calling static methods
   - Auth state becomes reactive (e.g., sign-out auto-closes Hive workspace via provider disposal)
   - Tests can override the provider with a mock

6. **AnalyticsService as an owned instance** — The timer lifecycle, buffer, and Hive writes should be managed by Riverpod's lifecycle. `ref.onDispose(() => timer.cancel())` replaces the manual `AnalyticsService.dispose()` in test teardown.

7. **SessionService + InstallService as providers** — These are read-heavy, write-light caches with clear lifecycle boundaries. Convert to providers, keep the cached values as provider state.

## The Migration Principle

**Do not do all 7 at once.** The risk is that a global find-and-replace breaks the 14 callers of `AuthService.signIn()` scattered across screens, providers, and services.

The right order:
1. Fix the bug (PolicyExtractionService auth) — takes 5 minutes, no coordination needed
2. Wire instance services as providers — additive, no existing code changes
3. Replace `authenticatedDio` with a provider — need to touch 5 consumers, but the change is mechanical (replace `DocumentService.authenticatedDio` with `ref.watch(authenticatedDioProvider)`)
4. Shrink the static surface (NotificationService, ContactService, etc.) — at this point the remaining static services are AuthService, AnalyticsService, SessionService, InstallService — the ones that actually benefit from a coordinated migration
5. Convert the Big 4 (AuthService, AnalyticsService, SessionService, InstallService) — coordinate with the workspace reset workflow since these touch startup ordering

Each step is independently deployable. Step 1 fixes a real production performance bug. Steps 2-3 make every future test easier. Steps 4-7 are the finishing move.
